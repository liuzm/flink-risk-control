# ADR-007：SaaS 平台边界与租户生命周期分层管理

## 背景

风控能力本身已具备，但若缺少明确的 SaaS 边界（平台/租户/应用/环境）的技术化定义，容易出现以下问题：

- 技术团队只优化规则链路，却忽略开通、支持、续费和停用流程。
- 资源迁移、配额停用、专属资源切换没有单一状态机，运维难复盘。
- 账单/配额与租户状态机脱节，出现“服务可用但账务失真”或“账务更新后流量仍走老额度”的不一致。

## 决策

1. 采用“平台化边界优先”的技术建模。
   - 平台、租户、应用、环境分别承担不同可见性与权限域。
   - 平台能力（开通、续费、支持、工单）与租户能力（规则、风险、成员）共享同一套 tenant/app/env 作用域，但由不同模块接口提供。
2. 引入明确的租户生命周期状态机作为发布、计量和运行一致性的入口条件。
   - PENDING → TRIAL → ACTIVE → PAUSED/SUSPENDED/RESTRICTED → CLOSED。
   - 控制面状态机直接影响运行面可写入与配额检查策略。
3. 统一 `scope` 与 `snapshotVersion` 为跨模块一致性的核心 ID。
   - 任何规则发布、账单口径、告警与审计都必须绑定 scope。
4. 将 SaaS 运维动作（支持、暂停、降级、资源迁移）作为标准化高权限命令，并写入与业务动作同级别的审计链。

## 备选方案

1. 聚焦规则引擎能力，暂不建全量平台域模型，仅在产品前端加壳。
   - 优点：上线更快。
   - 风险：难以在增长阶段稳定支持试用、计费、支持与治理。
2. 先做完全部微服务平台化，再引入共享内核。
   - 优点：概念清晰。
   - 风险：MVP 复杂度高、发布慢，且租户状态与规则发布协同难同步。

## 影响

- 提升长期可扩展性：平台能力与租户能力可并行演进。
- 提升可运营性：开通、停用、支持会话有统一轨迹。
- 降低跨团队沟通成本：产品、运维、财务使用同一租户状态。
- 实现上增加了“平台域状态机 + 运营动作模型”的初始开发量。

## 验证

- 在同一租户生命周期场景下，验证开通、试用、升级、停用、关闭的技术动作链路完整可回放。
- 验证平台态与租户态状态变化对决策入口、配额策略、发布流转是否产生一致影响。
- 验证支持会话、降级、暂停均可追溯到租户状态与审计动作。
- 验证跨资源隔离级别升级（共享→增强→专属）后，状态机与账务口径不丢失。
