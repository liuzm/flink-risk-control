# ADR-009：OpenAPI 对外服务与 Dubbo 内部服务契约分层

- 状态：已接受（V1 设计基线）
- 日期：2026-08-17
- 关联：
  - [API 与集成契约](../05-api-and-integration.md)
  - [技术选型方案](../15-technology-stack.md)

## 背景

平台将同时支持：

- 对外租户/合作方开放能力（决策、接入、账单、反馈、开发者工具）；
- 平台内部多个模块共享“底层服务能力”（如发布、配额、风险事实、处置、告警等）。

若没有明确分层，容易出现：

- 外部 REST 与内部服务接口语义漂移，导致联调频繁；
- 外部契约频繁变更拖慢内部部署；
- 内部服务直接绕过公共服务边界导致审计与权限一致性缺失；
- 对外与对内鉴权策略混淆，暴露过多内部调用入口。

## 决策

1. 采用双层协议策略：
   - 对外统一使用 **OpenAPI + HTTPS**，通过网关暴露；
   - 对内统一使用 **Apache Dubbo（Triple）**，提供服务内共享能力。
2. 对外契约的要求：
   - 必须有显式 `version`（如 `v1`）；
   - 与网关策略（限流、鉴权、幂等）绑定；
   - 变更遵循兼容性优先与协商冻结窗口。
3. 对内 Dubbo 契约的要求：
   - 与 OpenAPI 共享语义词典（`code`、`errorCode`、`snapshotVersion`、`requestId`、`tenantScope`）；
   - 支持灰度发布与多版本并存；
   - 服务端点仅允许来自受控内网与工作负载身份。
4. 同一领域能力可分别维护两套接口层：
   - OpenAPI 作为外部 API contract，面向消费者文档化；
   - Dubbo 作为内部服务 contract，面向稳定执行链路和高内网调用效率。
5. 在当前阶段控制面为模块化单体时，内部服务也必须以“接口先于实现”的方式定义，后续拆分不改字段语义。

## 备选方案

1. 全部接口都使用 OpenAPI + REST：
   - 优点：统一调用模型，学习成本低。
   - 风险：服务内聚合场景调用成本更高，契约臃肿。
2. 全部接口都使用 Dubbo：
   - 优点：统一内部协议。
   - 风险：对接外部合作方和 API 管理成本上升，发布可见性较弱。
3. 全量拆分为微服务并引入服务网格（Istio）：
   - 优点：治理能力最强。
   - 风险：V1 期间过早扩展，基础设施与维护负担高于收益。

## 影响

- 明确了“外部边界/内部共享边界”，便于权限、审计和安全隔离。
- 降低了契约混淆：消费者只看 OpenAPI 文档，平台内部服务通过 Dubbo 稳定协作。
- 为后续控制面逐步拆分到独立服务准备了统一服务接口与治理基础。
- 增加了双套契约维护成本，需要自动化同步校验机制（映射表、字段字典、CI 校验）。

## 验证

- 对外接口新增能力时，OpenAPI 与变更说明同步发布。
- Dubbo 接口新增能力时，与内部调用链路测试通过并具备版本兼容策略。
- 通过契约检查脚本验证至少 3 类关键对象（决策、发布、计量）在 OpenAPI 与 Dubbo 语义字段映射一致。
- 演练：禁用某一内部服务节点并验证路由、熔断与降级仍符合 OpenAPI 上下游用户体验。
